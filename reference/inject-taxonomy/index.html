03 — Inject Taxonomy

Every inject carries the common envelope (see 05-DATA-MODEL.md): id (I-07, I-07b for side injects), time (exercise clock H:MM), phase, from, to (target role), purposeTag, expectedAction, instructorNote, deliveryMode (hand-to-role, display-on-main-screen, play-audio, read-aloud), and 0..n assets.

Inject types

Section titled “Inject types”

Each type = fields + default render (template vs. AI vs. audio) + export behavior. T = HTML template → PNG/PDF. AI = ComfyUI image/video. TTS = ComfyUI/other voice. Composite types combine (AI photo dropped into a tweet template).

Domain tags

Section titled “Domain tags”

An inject type may carry a list of domains, such as ['airport', …]. A tagged type is offered only to projects whose domain profile has one of those ids: the MSEL prompt lists the domain’s types (the profile’s preferred types first), and a tagged type is treated as unavailable elsewhere, so generation falls back to the generic equivalent (fids_board → info_display_board, bhs_scada_screen → scada_hmi). Untagged types belong to every domain.

Types from packs and user templates

Section titled “Types from packs and user templates”

The tables above are the built-in list. A template in your own templates folder (userData/templates/injects/<type>/) or in an enabled pack whose type is not built in joins the taxonomy through the taxonomy block of its meta.json (category, render, defaultDelivery, optional domains and paper; a user template without the block joins as a hand-to-role document). The app registers these types at startup and after every pack change, so domain tags apply to pack types too. A pack template never replaces a built-in entry: a pack template that shadows a built-in type keeps the built-in taxonomy. A project’s own templates (including copies of pack templates kept after the pack is uninstalled) are listed with the project, and an inject’s stored type is any type id (lowercase letters, digits and underscores) so such injects keep loading.

Rendering rules

Section titled “Rendering rules”
  1. Text that players must read exactly (handles, flight numbers, IPs, timestamps) is always template-rendered. AI imagery is backgrounds, people, places, screens-from-a-distance.
  2. Every template ships schema.json (zod-compatible), preview.json, and renders in templates/injects/<type>/ at 2× scale; export to PNG and, for paper types, PDF.
  3. Templates accept project branding (org name, logo, airline names, city) via a brand object so NCIA/Akron/Cleveland references aren’t hard-coded.
  4. Audio: 44.1 kHz WAV master + MP3; optional post-FX chain (radio band-pass, phone compression, terminal ambience bed) defined in the type.
  5. Video: ≤ 15 s default, 720p, H.264 MP4; always also produce a poster PNG for the deck.
  6. Each asset records provenance: provider, model, workflow hash, prompt, seed — so it can be regenerated.
