Releasing

scripts/release.sh tags a release and creates a draft GitHub release; the release workflow (.github/workflows/release.yml) builds the macOS, Windows and Linux installers on GitHub-hosted runners, smoke-tests each and uploads them to the draft. The runners are free because the repository is public and the workflow uses standard runners only (ADR-0023).

Commands

Section titled “Commands”
Command What it does
pnpm build Build the app and the installers configured for this host OS into release/<version>/.
pnpm build:check Build an unpacked app only (release/<version>/mac-arm64/…); runs in pnpm ci:local.
pnpm package:smoke Test the packaged app (see Packaged smoke test). Run after pnpm build or build:check.
node scripts/package-smoke.mjs --dmg F The same against a .dmg: mounts it read-only, tests the app inside it, detaches.
pnpm icons Regenerate every icon from build/icon.svg (Electron rasterizes it; no design tools needed).
pnpm release <patch|minor|major|X.Y.Z> Dry run of a release (default). Add --publish to cut it.

Cutting a release

Section titled “Cutting a release”
  1. Merge everything for the release into main; check out main with a clean tree.
  2. In CHANGELOG.md, rename ## [Unreleased] to ## [X.Y.Z] - YYYY-MM-DD, add a fresh empty ## [Unreleased] above it, and merge that change through a PR.
  3. Dry run: pnpm release X.Y.Z. It checks the branch, tree and CHANGELOG section, runs pnpm ci:local, bumps the version in package.json temporarily, builds this host’s installers, lists them with sizes, prints the gh release create command and the release notes, then restores package.json. Nothing is committed, tagged, pushed or uploaded.
  4. Smoke-test the installer: node scripts/package-smoke.mjs --dmg "release/X.Y.Z/actionstations-X.Y.Z-mac-arm64.dmg".
  5. Publish: pnpm release X.Y.Z --publish [--issue N]. This runs pnpm version X.Y.Z (commit chore(release): vX.Y.Z (#N) + tag vX.Y.Z), pushes main and the tag, and creates a draft GitHub release with the CHANGELOG section as notes.
  6. The tag push starts the Release installers workflow (gh run watch). Each of its three jobs builds one installer on its own OS (macOS 15 arm64, Windows Server 2022 x64, Ubuntu 24.04 x64), runs pnpm package:smoke against it, and uploads the installer and its .sha256 file to the draft. It only ever uploads to a draft. To rebuild a draft’s installers, run the workflow by hand from the Actions tab with the tag.
  7. When all three jobs pass, review the draft on GitHub and publish it there.

Artifacts

Section titled “Artifacts”

artifactName is ${productName}-${version}-${os}-${arch}.${ext}:

Platform Target Example
macOS dmg, arm64 actionstations-0.1.0-mac-arm64.dmg
Windows NSIS, x64 actionstations-0.1.0-win-x64-setup.exe
Linux AppImage, x64 actionstations-0.1.0-linux-x86_64.AppImage

Measured on Apple M-series, Electron 45 (pnpm build, 49 s): the arm64 dmg is 263 MB; the app bundle is 672 MB on disk, of which app.asar is 208 MB and app.asar.unpacked 208 MB. The largest single item is onnxruntime-web (121 MB inside app.asar), which @huggingface/transformers pulls in next to onnxruntime-node.

Software bills of materials (#551)

Section titled “Software bills of materials (#551)”

Each release carries two CycloneDX 1.5 JSON SBOMs as release assets (not Actions artifacts):

  • actionstations-<version>-sbom.cdx.json: the desktop app’s production dependencies.
  • actionstations-relay-<version>-sbom.cdx.json: the self-hosted server’s (relay/node).

The sbom job in .github/workflows/release.yml runs node scripts/sbom.mjs (pnpm sbom locally; output goes to the ignored sbom-out/ folder) and uploads both files to the draft with the installers. The script reads pnpm list --prod --depth Infinity for the locked versions, so it needs no extra tool, no network and no paid service; each component has a package URL, its declared license and its place in the dependency graph. The file name carries the version, so link to a release tag: https://github.com/actionstations-ai/actionstations/releases/download/v<version>/actionstations-<version>-sbom.cdx.json.

What goes into the package

Section titled “What goes into the package”
  • app.asar: out/ (the electron-vite build), package.json and production node_modules. Excluded: source maps, TypeScript sources and declarations, Markdown, package-internal test/, tests/, __tests__/, __mocks__/, spec/ and fixtures/ folders, template __golden__/ images, and the C sources of better-sqlite3 (it ships Node-API prebuilds). Native binaries of the other operating systems (onnxruntime-node/bin/napi-*/<os>/) are dropped per platform.
  • Resources/app-resources/: templates/ (without goldens or tests), prompts/, comfy/.
  • app.asar.unpacked (asarUnpack in electron-builder.yml): code and data that must be opened with a real file path: better-sqlite3, sqlite-vec (loadExtension), onnxruntime-node, tesseract.js + tesseract.js-core + @tesseract.js-data/eng (OCR worker and language data), pdf.js standard fonts and the legacy pdf.js worker. electron-builder also unpacks every *.node file automatically (sharp, @napi-rs/canvas).
  • scripts/package-smoke.mjs fails if app.asar holds anything outside out/, node_modules/ and package.json, or any golden or package test folder.

Note for electron-builder.yml: a platform-level files list (mac.files, win.files, linux.files) must contain at least one positive pattern. A list with only exclusions makes electron-builder copy the whole repository (sources, reference/, and any untracked local files in the checkout) into app.asar, which is why each one restates out/**/*.

Electron fuses (#55)

Section titled “Electron fuses (#55)”

Set by electronFuses in electron-builder.yml (electron-builder’s built-in @electron/fuses integration, flipped right after packing):

Fuse Value Effect
RunAsNode off ELECTRON_RUN_AS_NODE is ignored; the binary cannot be used as Node.
EnableCookieEncryption on Cookie store encrypted with the OS keychain.
EnableNodeOptionsEnvironmentVariable off NODE_OPTIONS / NODE_EXTRA_CA_CERTS are ignored.
EnableNodeCliInspectArguments off --inspect* and SIGUSR1 cannot attach a debugger to the main process.
EnableEmbeddedAsarIntegrityValidation on app.asar is checked against the hash in Info.plist / the exe (mac, win).
OnlyLoadAppFromAsar on Electron loads the app only from app.asar.
GrantFileProtocolExtraPrivileges off file:// pages get no privileges beyond a browser’s; see below.

GrantFileProtocolExtraPrivileges can be off because the main and presentation windows load the renderer from app://bundle/index.html, a custom protocol that reads out/renderer out of app.asar (#117, ADR-0013). With loadFile() from file:// inside app.asar and the fuse off, the load fails (ERR_FILE_NOT_FOUND) and the window stays blank. Render and print windows still load temporary file:// documents, which needs no extra privileges.

Unsigned builds: flipping fuses invalidates Electron’s ad-hoc signature, which Apple silicon refuses to run, so resetAdHocDarwinSignature: true re-signs ad hoc. Remove it once a Developer ID signs the app (signing happens after the fuses are flipped).

Consequences for development and tests: unit tests (pnpm test) run on the unfused Electron from node_modules with ELECTRON_RUN_AS_NODE, so they are unaffected. Playwright’s _electron.launch() needs --inspect, so it cannot drive the packaged app; the packaged smoke test starts it with Chromium’s --remote-debugging-port and connects over CDP instead. That switch is a Chromium flag that no fuse controls; anyone able to start the app with arbitrary arguments can already run code as the user.

Packaged smoke test

Section titled “Packaged smoke test”

scripts/package-smoke.mjs runs static checks, then e2e/packaged.spec.ts with TTX_PACKAGED_APP set to the packaged executable:

  • the fuse wire in the Electron binary matches EXPECTED_FUSES (both wires of a universal binary), Info.plist carries ElectronAsarIntegrity, and app.asar holds only what may ship;
  • the app starts, creates a project and ingests a PDF (parsed in a worker thread), a DOCX and a PNG (tesseract OCR); search over the FTS5 + sqlite-vec index returns the right section for each; a ttx-media:// image from the project decodes in the renderer;
  • every inject template preview renders in the packaged render pool and matches its golden (templates/injects/*/__golden__), which also proves fonts and file:// template loading;
  • the renderer is served from app://bundle/ (webfonts load, the path guard answers 404 for directories and .. escapes), a rendered inject opens in the presentation window as a ttx-media:// image, and IPC works from that window;
  • runtime fuse probes: with ELECTRON_RUN_AS_NODE=1 the binary starts the app instead of running -e; --inspect=0 opens no debugger; a NODE_OPTIONS=--require script does not run (Electron also filters most NODE_OPTIONS in packaged apps, so the fuse itself is verified by the static check).

The spec is skipped when TTX_PACKAGED_APP is unset, so pnpm e2e is unaffected. Negative controls were run by flipping RunAsNode and EnableNodeCliInspectArguments back on in a copy of the app: both the static check and the runtime probes fail.

Platform-specific native dependencies

Section titled “Platform-specific native dependencies”

pnpm 10 installs only the optional platform packages for the machine it runs on. A build therefore bundles the native binaries of the host OS and CPU, and electron-builder prints “platform-specific optional dependencies not bundled” for every other platform (sqlite-vec-, @img/sharp-, @napi-rs/canvas-*). On a host build these warnings are expected and harmless. better-sqlite3 ships Node-API prebuilds for all platforms, and onnxruntime-node ships its binaries inside its own package.

To build for another CPU or OS, either:

  • build on the target OS: the release workflow does this for every release, and a checkout of the tag with pnpm install --frozen-lockfile && pnpm build does it by hand; or

  • cross-build after telling pnpm to install the other platforms’ packages, in pnpm-workspace.yaml:

    then pnpm install --frozen-lockfile (the lockfile does not change) and build, e.g. pnpm build:app && pnpm exec electron-builder --mac --x64.

    Undo it before the next host build with rm -rf node_modules && pnpm install --frozen-lockfile: a plain reinstall leaves the foreign packages in node_modules/.pnpm.

Each platform’s files list in electron-builder.yml keeps only that target’s native packages (@napi-rs/canvas-*, @img/sharp-*, @img/sharp-libvips-*, sqlite-vec-*, better-sqlite3/prebuilds/*) and leaves out onnxruntime-node’s other binaries (#382). onnxruntime-web is left out everywhere: transformers.js’s Node build bundles what it needs from it and runs on onnxruntime-node. package-smoke fails when an archive holds another OS’s, CPU’s or libc’s binaries, or onnxruntime-web. Measured on 0.4.0 content: Windows 360 → 290 MB, Linux AppImage 473 → 327 MB, macOS dmg 360 → 325 MB. A new native dependency needs its own exclusions there; adding a new target (Windows ARM64, Linux ARM64) means changing those lists.

Windows and Linux from a Mac

Section titled “Windows and Linux from a Mac”

Releases are built by the workflow now. Before it, both were cross-built on Apple silicon for 0.4.0 (macOS host, supportedArchitectures with os: [current, win32, linux]):

  • Windows: pnpm exec electron-builder --win nsis --x64. Build from a short checkout path (for example ~/Code/as-win): NSIS’s makensis aborts (SIGABRT) when an !include path is too long, which a worktree under /private/tmp/… exceeds.
  • Linux: pnpm exec electron-builder --linux AppImage --x64. For a quick native test on Apple silicon, also build --linux dir --arm64 -c.directories.output=release-arm64.

Testing Windows and Linux builds from a Mac

Section titled “Testing Windows and Linux builds from a Mac”

The release workflow runs package:smoke on each OS. For anything it does not cover (local models, a real install), test by hand:

  • Linux (Docker): run the AppImage in node:22-bookworm with --platform linux/amd64 (emulated) or the arm64 dir build with --platform linux/arm64 (native, much faster), under xvfb-run, with the GTK and NSS libraries installed. Under emulation the AppImage runtime fails with “Exec format error”: on a copy, zero bytes 8–10 (the AppImage magic), then --appimage-extract and run squashfs-root/actionstations. As root, Electron needs --no-sandbox: point TTX_PACKAGED_APP at a two-line wrapper script that adds it, then run e2e/packaged.spec.ts. The host’s Ollama is at http://host.docker.internal:11434.
  • Windows (VM): a Windows 11 ARM VM in UTM runs the x64 installer under emulation. With the SPICE guest tools installed, utmctl exec runs commands (as SYSTEM, without output: write to a file and utmctl file pull it) and utmctl ip-address finds the VM. Install silently with setup.exe /S /allusers /D=C:\as\app, start the app with --remote-debugging-port=9222, expose it with netsh interface portproxy and a firewall rule, and drive it from the Mac over CDP (chromium.connectOverCDP). Remove the port proxy and rule afterwards.
  • Template goldens are macOS renders. On Linux and Windows, glyph placement and line height differ by about a pixel, so packaged.spec.ts holds only the page geometry there (#383): same width, height within 1% (Linux) or 2% (Windows); compare the images by eye when a template changes.

Replacing a published file

Section titled “Replacing a published file”

gh release upload --clobber deletes the old asset, and GitHub’s download count for it restarts at zero. pnpm stats keeps the earlier count (see CONTRIBUTING, Repository stats); run it before replacing a file.

Intel macOS (x64) was cross-built this way on Apple silicon and passed the packaged smoke test under Rosetta (first start under Rosetta takes over 30 s). Caveat: onnxruntime-node ships no darwin/x64 binary, so the optional local ONNX embedder is unavailable on Intel Macs; the built-in and provider embedders work. A universal mac build is not configured: it would need both slices’ native modules and x64ArchFiles for the .node files.

Code signing (not configured)

Section titled “Code signing (not configured)”

No certificates exist yet: mac.identity is null and Windows builds are unsigned. Keep every credential in environment variables or the OS keychain, never in the repository.

macOS: Developer ID + notarization

Section titled “macOS: Developer ID + notarization”
  1. Join the Apple Developer Program, create a Developer ID Application certificate, and install it in the login keychain (or export it as a .p12).
  2. In electron-builder.yml (mac): delete identity: null (electron-builder then picks the Developer ID from the keychain; or set identity: "Your Name (TEAMID)"), add notarize: true, and delete resetAdHocDarwinSignature under electronFuses. hardenedRuntime and build/entitlements.mac.plist (JIT, unsigned executable memory, disabled library validation for the unpacked native modules) are already set.
  3. Provide credentials through the environment when building:
    • certificate from a file instead of the keychain: CSC_LINK=/path/to/cert.p12, CSC_KEY_PASSWORD=…;
    • notarization, preferably with an App Store Connect API key: APPLE_API_KEY=/path/to/AuthKey_XXXX.p8, APPLE_API_KEY_ID, APPLE_API_ISSUER (alternatives: APPLE_ID + APPLE_APP_SPECIFIC_PASSWORD + APPLE_TEAM_ID, or APPLE_KEYCHAIN + APPLE_KEYCHAIN_PROFILE).
  4. Verify: codesign --verify --deep --strict --verbose=2 "Action Stations.app", spctl --assess --type execute -vv "Action Stations.app", and xcrun stapler validate "actionstations-X.Y.Z-mac-arm64.dmg"; then pnpm package:smoke (signing must not disturb the fuses or asar integrity).

Windows: Authenticode

Section titled “Windows: Authenticode”

Code-signing certificates now live on hardware tokens or cloud HSMs, so pick one of:

  • Azure Trusted Signing: add win.azureSignOptions (publisherName, endpoint, certificateProfileName, codeSigningAccountName) and provide AZURE_TENANT_ID, AZURE_CLIENT_ID, AZURE_CLIENT_SECRET in the environment.
  • A certificate on a token / in the Windows store: add win.signtoolOptions with certificateSubjectName or certificateSha1, publisherName, and signingHashAlgorithms: [sha256]; build on Windows with the token present.

Verify with signtool verify /pa /v "actionstations-X.Y.Z-win-x64-setup.exe".

Until then: installing unsigned builds

Section titled “Until then: installing unsigned builds”
  • macOS: Gatekeeper blocks the first launch. On macOS 15 and later, open System Settings → Privacy & Security and click Open Anyway (right-click → Open no longer bypasses it); on macOS 14 and earlier, right-click the app → Open. Or run xattr -dr com.apple.quarantine "/Applications/Action Stations.app".
  • Windows: SmartScreen shows “Windows protected your PC” → More info → Run anyway.
  • Linux: chmod +x the AppImage and run it.
