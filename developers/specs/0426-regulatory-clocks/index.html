Spec 0426: Regulatory clocks and compliance mapping

Issue: #426 · Milestone: 0.7.0 · Status: Partly implemented (see Implementation notes) · Depends on: — · Related: #417 (session log), #419 (AAR/IP draft), #420 (Excel MSEL), #421 (Core Capabilities, EEGs), #416 (evaluator observations), #428 (controller tools)

Summary

Section titled “Summary”

Facilitate shows countdown clocks for the reporting deadlines that apply to the exercising organization, such as SEC Form 8-K Item 1.05, CIRCIA, TSA directives, HIPAA, GDPR, NIS2 and DORA. An inject starts a clock, or the facilitator starts one by hand. The facilitator records when players filed, and the AAR states which deadlines were met. Regulations and framework controls (NIST CSF 2.0, NIS2 Article 21, DORA) are pack data, not code. A coverage matrix export lists the controls each MSEL row exercised, with the evidence for each.

Requirements

Section titled “Requirements”

User stories

Section titled “User stories”
  • As a facilitator of a cyber exercise, I want a CIRCIA 72-hour clock to start when the “ransomware confirmed” inject is delivered, so that players feel the reporting pressure and I can see whether they would have met it.
  • As an exercise planner at a public company, I want an SEC 8-K clock that starts only when players decide the incident is material, so that the exercise tests the materiality call.
  • As a CISO, I want a coverage matrix of which NIST CSF 2.0 subcategories the exercise exercised, so that I can show the board and auditors what we tested.
  • As a pack author in the EU, I want to add my national NIS2 transposition deadlines as data, so that I do not have to wait for an app release.

Functional requirements

Section titled “Functional requirements”
  • FR-1 Two new pack content kinds: regulations/<id>.json (reporting obligations with one or more clocks) and frameworks/<id>.json (control catalogs with mapping rules). Schemas Regulation and Framework live in src/shared/schemas/compliance.ts. Packs that carry them declare formatVersion: 2 (Design §2).
  • FR-2 DomainProfile gains optional regulations: string[] and frameworks: string[], the ids that apply to the domain by default. Older apps drop the unknown keys (z.object), so existing packs and projects keep working.
  • FR-3 Per project, Settings › Compliance lists the regulations and frameworks the profile suggests, plus any others from installed packs. Each can be switched on or off (stored in project.json compliance). Each regulation shows its status (in force, proposed, guidance), its source link and the date its values were last checked. For a proposed regulation, the UI states that the deadline is from a proposed rule.
  • FR-4 A regulation defines triggers (named events such as “became aware”, “materiality determined”, “classified as major”) and clocks. A clock’s deadline is a duration (hours, calendar_days, business_days, months) from a trigger or from another clock’s completion. It can also be the earliest of several such terms (DORA: 4 h after classification, but no later than 24 h after awareness).
  • FR-5 Business days use a calendar named in the regulation: us_federal (weekends and US federal holidays, observed rule), weekdays, or none. The app computes US federal holidays by rule (no network) in src/shared/compliance/calendars.ts. Other calendars can be added later as data (Open question 3).
  • FR-6 Triggers fire in three ways: (a) An MSEL row carries triggers: [{ regulationId, triggerId }], and delivering the row in Facilitate fires them at the delivery’s scenario time. (b) The facilitator fires a trigger by hand from the clocks panel (“Players determined materiality at 10:40”). (c) With live play (#418), a controller can fire a trigger from a player message.
  • FR-7 Facilitate shows a Clocks strip under ExerciseClock. Each running clock shows the regulation, the filing, the scenario-time deadline (date, weekday, time), the time left in scenario time and a status (running, due soon at 25 % left, overdue, met, missed, waived). Completing a clock (“Filed at…”) can start dependent clocks.
  • FR-8 Clocks run on scenario time: the scenario’s start date and startWallClock plus the exercise clock. Time jumps that move the exercise clock move the clocks with it. When the scenario has no start date, the app reads it from the STARTEX card (the date parser behind the DATE_DRIFT lint). Failing that, it uses the next Monday, and a visible note says business days assume that date.
  • FR-9 The presentation window can show selected clocks (“Show on screen”), off by default. The room sees “CIRCIA report due in 61 h 12 m”, never the facilitator’s notes.
  • FR-10 Every trigger, completion and waiver is written to facilitator.json and to the session log (#417) as compliance.trigger / compliance.clock entries.
  • FR-11 A framework defines its control hierarchy (for example function › category › subcategory) and mapping rules. Each rule matches on purpose tag, inject type, threat family, regulation trigger and keywords (in the row event or expected action) and gives control ids. Rules run when the MSEL is generated or edited and suggest MselRow.controls. The user accepts or removes the suggestions in the MSEL editor. Accepted ones are stored, and manual additions are allowed.
  • FR-12 Optional model-assisted mapping: Suggest controls runs the critique text task with a ComplianceMapOutput JSON schema over the rows and the enabled control list. The results are shown as suggestions, never stored automatically. The button names the routed provider. A cloud provider shows what is sent (#433 when available).
  • FR-13 Evidence levels per control, in order: planned (a row maps to it), delivered (that row was delivered in Facilitate), observed (a note, quote (#425), evaluator observation (#416) or met clock references the row or control). A met clock is evidence for the controls its regulation lists in controls. A missed clock is shown as a gap.
  • FR-14 Coverage matrix export: new targets coverage_xlsx and coverage_csv in EXPORT_TARGETS. The Markdown and DOCX scenario exports also gain a “Compliance coverage” section. Columns: framework, hierarchy path, control id, title, rows (ids), evidence level, evidence references, and the regulatory clocks with deadline, filed time and result. There is one sheet per framework, plus a “Clocks” sheet.
  • FR-15 The AAR draft (#419) receives clock results and the coverage summary as inputs with cite keys (K<n> for clocks, F<n> for controls).
  • FR-16 Bundled data (core pack, packs/regulations/, packs/frameworks/) ships the regulations in Design §5 and the NIST CSF 2.0, NIS2 Article 21 and DORA catalogs. Each record has source, citation, status and verifiedOn. A unit test fails when verifiedOn is older than 12 months, so each release re-checks the deadlines.

Non-functional requirements

Section titled “Non-functional requirements”
  • NFR-1 Cost: no service. All data is in packs. NIST CSF 2.0 is a US Government work. EU legislation text may be reused under Commission Decision 2011/833/EU, and the catalogs carry ids, titles and short summaries, not the full legal text (CONTRIBUTING, Project rules 1).
  • NFR-2 Privacy: nothing leaves the computer. FR-12 calls only the provider the user routed critique to, and only on click (Project rules 3).
  • NFR-3 Accessibility: WCAG 2.2 AA. Clock status uses text and icon, not color alone. Countdown updates are not announced every second. The live region announces only status changes (due soon, overdue, met). The room display uses at least 48 px numerals and AA contrast in light and dark themes.
  • NFR-4 Correctness: clock math is pure and deterministic (src/shared/compliance/clock.ts), with table-driven tests for every bundled regulation, DST changes and holidays. A clock computed in the renderer and in export gives the same deadline.
  • NFR-5 Not legal advice: every regulation card and export carries the line “Exercise aid, not legal advice. Check the current rule and your counsel.” Regulations with status: 'proposed' are labeled in the panel and in exports.

Out of scope

Section titled “Out of scope”
  • Filling or submitting real regulatory forms (regulatory_report_form stays a template for injects).
  • Determining whether a regulation applies to an organization; the user switches it on.
  • Bundled state breach-notification laws (packs may add them; Open question 2).
  • ISO 27001, SOC 2, PCI DSS and other licensed catalogs (copyright; Open question 4).

Design

Section titled “Design”

1. Schemas (src/shared/schemas/compliance.ts)

Section titled “1. Schemas (src/shared/schemas/compliance.ts)”

Keywords are plain lowercase words, not regex, so pack data cannot add a backtracking pattern (the domain regex rule in docs/packs-format.md stays the only regex surface).

Scenario and facilitator additions:

FacilitatorState changes from z.object to z.looseObject. Live play and #428 add keys to it too, and a key one build does not know must survive a save by another build. Each feature adds one optional top-level key and does not touch the others.

2. Pack format

Section titled “2. Pack format”
  • PACK_KINDS gains regulations and frameworks (flat, <id>.json, id ^[a-z][a-z0-9_]*$, 1 MB per file cap for frameworks).
  • PACK_FORMAT_VERSION becomes 2. The reader accepts 1 and 2. A version-1 manifest that lists the new kinds is refused, and an app that only knows 1 refuses version 2 with the existing “this pack needs a newer version of the app” message. That message is clearer than the “unknown contents key” error an old app would otherwise show. scripts/build-bundled-packs.mjs writes version 2 only for packs that contain the new kinds.
  • docs/packs-format.md gets the new folders, ids, the per-kind content checks (zod parse, every MappingRule.controls/Regulation.controls reference resolves, every ClockTerm.from names a trigger or an earlier clock with no cycles) and two example blocks parsed by pack.test.ts.
  • Bundled sources: packs/regulations/*.json and packs/frameworks/*.json, mapped to ai.actionstations.core in packs/bundled.json. Domain profiles in packs/domains/*.json list the defaults: for example airport lists tsa_aviation_cyber and circia, healthcare lists hipaa_breach and circia, financial_services lists sec_8k_105, and generic lists none.
  • Registry: src/main/packs/state.ts registers regulations and frameworks the way it registers domains. Layer precedence is the same: project > user > installed > bundled. A project that uses one copies it into <project>/compliance/<kind>/<id>.json and records it in packs.json (ADR-0018 copies), so a shared project keeps its deadlines.

3. Clock engine (src/shared/compliance/)

Section titled “3. Clock engine (src/shared/compliance/)”
  • Scenario times are floating local times, with no time zone stored. The organization’s local time is the narrative. DST is ignored on purpose: an exercise does not cross a real DST change, and the test table pins that behavior.
  • business_days: a deadline of N business days lands at the same time of day on the Nth business day after the trigger date. Example: 4 business days from Thursday 10:40 is the next Wednesday 10:40 with no holiday. With a Monday federal holiday in between, it is Thursday 10:40. The rule text tells the facilitator to read the regulation for end-of-day filing conventions.
  • months: calendar month addition, clamped to the month’s last day.

4. Main and IPC

Section titled “4. Main and IPC”
  • src/shared/ipc/compliance.ts (new domain file), handlers src/main/ipc/handlers/compliance.ts:
    • compliance:list { projectPath } → enabled and available regulations and frameworks, with provenance (pack id/version, as in ProvenanceBadge)
    • compliance:set { projectPath, regulations?, frameworks? } → project compliance
    • compliance:suggest-rules { projectPath, scenarioId } → MselRow.controlSuggestions recomputed (pure rules, src/main/compliance/rules.ts)
    • compliance:suggest-model { projectPath, scenarioId, rowIds? } → { jobId } (job kind compliance-map, critique task, ComplianceMapOutput in schemas/generation.ts)
    • compliance:coverage { projectPath, scenarioId } → CoverageReport (used by the panel, the export and #419)
  • Firing and completing clocks is a FacilitatorState update through the existing facilitator:state-save path (renderer reducers in routes/facilitate/compliance.ts). No extra channel is needed.
  • Generation: after each msel_phase step the pipeline runs the rules (no model call) and stores suggestions. prompts/msel_phase.md gets one optional variable, regulations, a short list of enabled triggers, so the model can place a trigger row (“Legal confirms materiality”). It writes triggers on that row. The output schema MselPhaseOutput gains triggers (optional).
  • Export: src/main/export/coverage.ts builds the CoverageReport into sheets with exceljs (already a dependency) and CSV. views.ts adds the Markdown/DOCX section. run.ts wires the two new targets.

Security and privacy

Section titled “Security and privacy”
  • Pack data is untrusted. It is parsed with zod with caps on every list and string. Keywords are plain words, there are no regexes, and URLs must be http(s). They render as text and open in the system browser through the existing external-link guard.
  • FR-12 sends row text and control titles to the routed critique provider. It is never automatic, the provider is named on the button, and the #433 preview applies.
  • No regulator is contacted, nothing is filed and no network call is made.
  • Legal-advice disclaimer (NFR-5) on the panel, settings and every export.

Testing

Section titled “Testing”
  • Unit: calendars.test.ts (US federal holidays 2024–2030 against a fixed table, including Juneteenth and observed Saturday/Sunday holidays). clock.test.ts, table-driven per bundled regulation: 8-K over a holiday weekend, DORA earliest-of terms, NIS2 chained clock, months clamping, a clock that waits for its trigger. Scenario time from the STARTEX date fallback. The rules engine on fixture rows. The schema cross-checks (cycle, dangling references). The verifiedOn freshness test (FR-16).
  • Pack: pack.test.ts parses the new doc examples. The reader refuses a v1 manifest with new kinds, and refuses v2 on a simulated v1 app. build-bundled-packs maps every regulation/framework to exactly one pack.
  • Component: clocks strip states and keyboard operation, MSEL row drawer chips.
  • Export: coverage.test.ts snapshot of CSV, and XLSX sheet names, headers and row counts read back with exceljs.
  • e2e: open the airport example, enable CIRCIA, deliver the trigger row, check the clock deadline text, mark it met, export coverage_xlsx, assert the file and the “Clocks” sheet.

Section titled “Implementation notes (first pull request)”

Built: tasks 1 to 5 and 7 except where listed below, with the deviations below. The rest is follow-up work tracked in its own issue.

Differences from the design above, and why:

  • MselRow.triggers, controls and controlSuggestions are optional (absent = none) rather than .default([]): a defaulted field becomes required in the output type, which would change every place that builds a row in code, and an absent field reads the same.
  • FacilitatorState.compliance is optional too (one optional top-level key per feature, as §1 says). A fired trigger stores exerciseMin (the clocks count from it, so a time jump or a later start-date change moves them correctly) and scenarioAt as a floating local date-time YYYY-MM-DDTHH:MM (LocalDateTime), not an IsoDateTime with an offset: scenario time has no time zone (§3). Completions store exerciseMin and scenarioAt the same way.
  • A filing recorded after the deadline shows as missed (filed late).
  • A clock that is due at the earliest of several terms uses the terms whose start is known; it waits only when none is known. The DORA initial notification therefore runs from awareness (24 h) and can only move earlier when the incident is classified as major (4 h).
  • Framework.shortLabel (≤ 31 characters) names the framework’s sheet in the workbook, since Excel sheet names are limited to 31 characters.
  • Settings › Compliance lives in Project settings on the project Overview (routes/project-home/ComplianceSettings.tsx), because routes/settings/ is the app-wide settings page and the switches are per project.
  • Layer precedence is project copy > installed pack > bundled pack (there is no user layer for this data). Only items from an installed pack are copied into the project when switched on; bundled items are read from the app, so a corrected deadline in a release reaches every project (the rule bundled templates follow, ADR-0040).
  • The coverage matrix lists every leaf control of each enabled framework (so gaps are visible), with “Accepted” or “Suggested” for its mapping. Mapping rules run when the coverage is built rather than being stored on the rows. coverage_csv writes two files, the matrix and the clocks. The Markdown export gains the “Compliance coverage” section; the Word documents do not yet.
  • The MSEL editor gets Row actions → Starts reporting clocks… (a dialog), and the Facilitate timeline marks such rows “Starts a reporting clock”. ScenarioBrief.startDate is set in the brief form of a new scenario.

Open questions

Section titled “Open questions”
  1. CIRCIA while the rule is not final. Ship it on by default for critical-infrastructure domains, or off? Recommendation: on for the domains that list it, labeled “proposed rule”. Exercising the expected 72 h/24 h clocks is the point of the feature, and the label avoids overstating it. Update the record when the final rule publishes (a pack update, no app release).
  2. State breach-notification laws. Recommendation: do not bundle them in 0.7.0. There are more than 50 laws with frequent amendments. Document the format and invite community packs (#441). Bundle none until someone can keep them current.
  3. Non-US business-day calendars (EU member states, UK). Recommendation: add a holidays array (ISO dates) to Regulation in a later format bump. For 0.7.0, EU regulations use hours and calendar months only, which is how NIS2 and DORA state them.
  4. ISO 27001 / SOC 2 / PCI DSS mapping. These catalogs are copyrighted. Recommendation: support them only as user or pack data the user supplies (ids and the user’s own titles), never bundled.
  5. Clocks on players’ devices (live play). Recommendation: yes, read-only, behind the same “Show on screen” switch, sent as part of clock.state so devices need no extra message type.
