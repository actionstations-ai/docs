Spec 0436: Map view of injects

Issue: #436 · Milestone: 0.9.0 · Status: Mostly implemented (0.9.0 PR 1; follow-ups #500). Map on devices (map.state), tile pyramid, offline place labels and Locations pages for geo maps are built (#500). Still open: packaged WebGL check, a rendered basemap picture for exports. Changes: maps:snapshot takes { projectPath, scenarioId, mapId, audience } (site plans only) and draws with map_annotation; Locations pages are HTML pages drawn from project data · Depends on: #444 for FR-14 · Related: #417 (controller dashboard), #411/#412 (player page, inject delivery), #439 (live hazard data), #440 (regional exercises), #442 (update notifications), facility facts (#143)

Summary

Section titled “Summary”

Injects can be placed on a map:

  • A site plan: an image or PDF page of the facility, such as a terminal plan, a dam’s site drawing or a campus map. Places are pinned by percentage coordinates.
  • A geographic map: places are pinned by latitude and longitude. The map data comes from one of three sources:
    • online tiles, off until the user turns them on;
    • an offline map file per US state that Action Stations publishes;
    • a small area around a site downloaded from OpenFreeMap, or the user’s own PMTiles or MBTiles file.

Facilitate gets a Map tab that shows delivered, due and upcoming injects at their places. The presentation window and, optionally, players’ devices show the delivered ones. Every download is started by the user, verified, resumable and attributed.

Requirements

Section titled “Requirements”

User stories

Section titled “User stories”
  • As an exercise planner, I want to drop the terminal plan PDF in and pin “Gate A1”, “BHS room” and “AOC”, so that every inject that happens there shows on the map.
  • As a facilitator, I want to see where the delivered injects are and what is coming next, so that I can tell the room “the second alarm is across the airfield”.
  • As a facilitator in a room with no internet, I want the Ohio map file on my laptop, so that the exercise does not depend on the venue’s Wi-Fi.
  • As a planner preparing at my desk, I want online maps while I place staging areas, so that I do not have to download anything first.
  • As a regional planner (#440), I want a street map of the county with the staging areas, so that agencies see the same picture.

Functional requirements

Section titled “Functional requirements”

Maps and places

  • FR-1 Project-level maps in <project>/maps/maps.json, at most 20, one default. Each map is a site_plan (an image in the project) or a geo map (a basemap source, see FR-9).
  • FR-2 Add site plan imports .png .jpg .webp (≤ 50 MP) or one page of a .pdf (rendered at 200 dpi, capped at 8000 px on the long edge). The original goes to maps/<mapId>/source.<ext> and the display image to maps/<mapId>/plan.png. A project document of kind map (DocumentMeta.kind) can be used directly (“Use as site plan”).
  • FR-3 Places are project-level, named points or areas shared by all scenarios: { id, label, kind, positions[] }. A position is either { mapId, x, y } in percent of a site plan (0–100 from the top-left, the same convention as the map_annotation template) or { mapId, lat, lon } on a geo map. An area is a polygon of up to 32 points. A place can link to a facility fact (factRef: "<categoryId>:<entry>", for example gates:A1).
  • FR-4 A Places editor lets the user pan and zoom, drop a pin, draw an area, name it, and choose a kind (incident, staging, command, asset, public, other). It can also link a fact, and Pin facility facts lists fact entries not yet placed so they can be dragged onto the map.
  • FR-5 MSEL rows reference places with MselRow.placeIds (≤ 5). There is a picker in the MSEL editor, and the names show in the Facilitate side panel.
  • FR-6 Generation: msel_phase receives place labels (≤ 60, fact-linked first) and may return placeIds. Unknown ids are dropped by the deterministic repairs. A rule pass fills placeIds when a row’s event text names a place label or its fact entry exactly (word-boundary match, case-insensitive), with no model call.

Facilitate

  • FR-7 A Map tab beside the timeline. Pins are drawn per row: delivered (filled, with the row id), due (filled with a ring and “due” in the legend), upcoming (outlined, hidden unless “Show upcoming” is on, so the screen can be shared without spoilers). Selecting a pin selects the row and the reverse. Several rows at one place form a numbered cluster.
  • FR-8 Show map on screen sends the map to the presentation window with delivered pins only, labels and a legend. It follows the Facilitate view unless unlinked. Exports: the MSEL PDF and controller handbook can include “Locations” pages rendered with the map_annotation template (≤ 12 markers per page, split across pages). With live play, Map on devices sends a map.state message (session protocol #406): the map id, a raster snapshot or site plan hash, and delivered pins for that role’s injects only.

Basemap sources for geo maps

  • FR-9 A geo map has one basemap source: online (FR-10), catalog (an installed state file, FR-14), area (an OpenFreeMap area download, FR-15) or file (an imported archive, FR-16). The map can switch sources without losing places, because places are stored in latitude and longitude.
  • FR-10 Online maps are off by default (CONTRIBUTING, Project rules 3). Settings › Maps has a switch with the text: “When on, the map provider receives your computer’s IP address and the map tiles for the area you view. Nothing else from your project is sent.” Providers:
    • OpenFreeMap (default): vector tiles from https://tiles.openfreemap.org/styles/<style> (Liberty, Positron, Bright, Dark). No API key, no request limit, commercial use allowed. Attribution “OpenFreeMap © OpenMapTiles Data from OpenStreetMap”.
    • OpenStreetMap standard: raster tiles from a configurable HTTPS URL (default https://tile.openstreetmap.org/{z}/{x}/{y}.png) for interactive viewing only, under the OSM Foundation tile usage policy (FR-11).
    • Custom: a MapLibre style URL or a raster/vector tile URL template the user enters, with an attribution field that must be filled.
  • FR-11 OpenStreetMap standard tiles follow the tile usage policy:
    • HTTPS URL only, and the URL is configurable.
    • Requests send the distinct User-Agent ActionStations/<version> (+https://actionstations.ai).
    • The cache honours Cache-Control, Expires and ETag (conditional requests), and keeps a tile at least 7 days when the headers do not say.
    • Attribution “© OpenStreetMap contributors” is visible and links to https://www.openstreetmap.org/copyright.
    • No prefetching (MapLibre prefetchZoomDelta: 0, no off-screen tiles), no bulk download, no offline save. The OSM cache is not exportable and is never offered as a download source.
  • FR-12 Online requests go through the main process (Design §3), so the User-Agent, cache and host checks hold regardless of the renderer. With online maps off, no request leaves the computer, and a geo map with an online source shows “Online maps are off. Turn them on in Settings › Maps or choose offline map data.”
  • FR-13 All downloads (FR-14, FR-15) are started by the user and run as jobs:
    • progress and Cancel;
    • resume after Cancel, crash or restart (HTTP Range with If-Range on the stored ETag, and skip-existing for tiles);
    • a byte cap;
    • sha256 verification before the file is used. The app uses sha256 rather than BLAKE3 because Node’s crypto has it, so no new native dependency is needed (Open question 5).

Offline map data

  • FR-14 State map files. The app reads a catalog (https://github.com/actionstations-ai/maps/releases/latest/download/catalog.json) only when the user opens Download a state map or clicks Check for updates. The catalog lists one PMTiles extract per US state, DC and each territory, with size, sha256, bounds, zoom range, build date and attribution.

    • The user picks a state, sees the size and free disk space, and downloads it.
    • Check for updates compares the installed sha256 with the catalog. The new version is downloaded and verified before the old one is removed, and projects that use the state switch to the new file.
    • With #442 update notifications on, the monthly catalog can be checked with the app’s update check. Otherwise only by click.
    • The files are produced by the #444; see Design §6.

  • FR-15 Area around a site. The user draws a box (on a state or online map, or by typing W,S,E,N) and picks a zoom range. The app downloads OpenFreeMap vector tiles for the box within OpenFreeMap’s offline terms:

    • at most 3,000 tiles and at most 50 MB per download (the plan is refused above 3,000 tiles, and the download stops at 50 MB);
    • at most 4 parallel requests;
    • the unique User-Agent above.

    The result is a local MBTiles archive with the style’s attribution. The estimate (“1,840 tiles, about 22 MB”) is shown before the download starts. This works even with online maps off, because it is a separate user action that names the host it contacts.

  • FR-16 Import your own .pmtiles (vector in the Protomaps or OpenMapTiles schema, or raster PNG/JPEG/WebP) or .mbtiles (raster or vector), ≤ 4 GB. The app reads the header and metadata (bounds, zooms, attribution) and refuses archives without bounds. The user must enter an attribution when the metadata has none.

  • FR-17 Styles, glyphs (Latin script) and sprites for offline rendering ship with the app:

    • the Protomaps basemap style for Protomaps-schema archives (state files);
    • an OpenMapTiles-schema style for OpenFreeMap areas and OpenMapTiles imports, which is OpenFreeMap’s Liberty or Positron style rewritten to local sources; task 5 confirms the license.

    Rendering offline needs no network.

  • FR-18 Attribution is always visible: bottom right on every geo map, on the presentation window, on devices and on exported pages, taken from the source’s metadata. It cannot be hidden. Exports also list the map source and build date.

Non-functional requirements

Section titled “Non-functional requirements”
  • NFR-1 Cost: nothing paid (CONTRIBUTING, Project rules 1).
    • OpenFreeMap and OSM are free.
    • State files are GitHub release assets of a public repository, built by a free GitHub Actions workflow (ADR-0023). Release assets have no bandwidth charge, and each file is under the 2 GiB per-file limit.
    • Libraries: MapLibre GL JS (BSD-3-Clause) and pmtiles (BSD-3-Clause). The Protomaps basemaps-assets are BSD-3 code with OFL fonts.
  • NFR-2 Privacy: no network until the user turns on online maps or starts a download. The settings text names what the provider sees (FR-10). Requests carry no cookies, no referrer and no project data. Tiles never go to a model provider.
  • NFR-3 Accessibility: WCAG 2.2 AA.
    • A “Locations” list (row id, place, status) mirrors the map, so screen reader and keyboard users work from the list.
    • Map controls are labeled buttons, and pin states differ by shape and text.
    • prefers-reduced-motion turns off fly-to animation.
    • Download progress is announced at 25 % steps.
  • NFR-4 Performance:
    • An 8000 × 6000 site plan pans and zooms at 60 fps on integrated graphics (tile pyramid, Design §4).
    • A local tile request through IPC takes < 10 ms median.
    • The Map tab adds < 20 MB of renderer memory with a 200-row MSEL.
    • Hashing a 2 GB state file takes < 15 s on an M1 (streamed sha256).
  • NFR-5 Platforms: macOS arm64, Windows x64, Linux x64. MapLibre needs WebGL. Without it, site plans still work (canvas renderer), and geo maps show “This computer cannot draw vector maps. Use a raster archive or a site plan.”
  • NFR-6 Storage: state files go in a shared app-level store (Design §2). The Maps settings page shows each installed file, its size, the projects that use it, and Delete.

Out of scope

Section titled “Out of scope”
  • Georeferencing a site plan to latitude/longitude (Open question 2).
  • Routing, distances, live unit positions, 3D and indoor multi-floor maps (a floor is a separate site plan).
  • Live hazard overlays (#439).
  • Keyed commercial map providers (Google, Mapbox, Esri). A custom URL may point at one, but the app does not integrate or store keys for them.
  • State files outside the US (Open question 6).

Design

Section titled “Design”

1. Data model (src/shared/schemas/maps.ts, new)

Section titled “1. Data model (src/shared/schemas/maps.ts, new)”
  • MselRow.placeIds: z.array(SafeId).max(5).default([]) in src/shared/schemas/scenario.ts.
  • FacilitatorState (a looseObject per specs 0426/0428) gains map: { mapId?, showUpcoming, onScreen, onDevices, view? }.
  • AppSettings.maps (src/shared/schemas/settings.ts): { online: { enabled: false, provider: 'openfreemap', style: 'liberty', osmUrl?, customUrl?, customAttribution? }, catalogUrl (default above), checkUpdates: false }.

2. Where archives live: a shared app-level store

Section titled “2. Where archives live: a shared app-level store”

The decision is a shared app-level store, not the project folder. A state file is up to 2 GB. Planners keep several projects for organizations in the same state: tabletop series, the regional exercises in #440, examples. One file per state, referenced by every project that needs it, avoids copying gigabytes per project. Content addressing (sha256) gives deduplication and lets a project say exactly which data it was built on. A project stays git-friendly with nothing to ignore.

The cost is portability. A project copied to another computer refers to archives that are not there. Two mitigations:

  1. The map shows “Map data for Ohio is not on this computer” with Download Ohio (catalog) or Locate file (area/file). The app then hashes the file the user locates and accepts it only if its sha256 matches.
  2. Copy map data into the project (per map) copies the archive to maps/<mapId>/<sha256>.<ext>, which PROJECT_GITIGNORE ignores. The project then resolves the project copy first.

Site plans stay in the project: they are the organization’s own material and small.

3. Main process (src/main/maps/)

Section titled “3. Main process (src/main/maps/)”

Allowed hosts:

Use Hosts

4. Renderer

Section titled “4. Renderer”
  • components/map/MapView.tsx has two engines:
    • SitePlanEngine: a <canvas> over plan-tiles/, with no WebGL.
    • GeoEngine: MapLibre GL JS with maplibregl.addProtocol('asmap', …). asmap://<mapId>/{z}/{x}/{y} → maps:tile IPC → main resolves the map’s source (project copy, store archive or online.ts). Styles, glyphs and sprites come from asmap://assets/… in the app bundle. For online OpenFreeMap the remote style JSON is fetched by main once per session and its source, glyph and sprite URLs are rewritten to asmap://online/…, so the renderer never fetches http(s).
  • The CSP in src/renderer/index.html keeps connect-src 'self' ttx-media:. Task 4 picks MapLibre’s CSP build (separate worker file) to avoid worker-src blob:. If that is not possible, the CSP adds worker-src 'self' blob: only.
  • src/shared/maps/pins.ts pinsFor(scenario, injects, state, places, mapId, audience) is shared by Facilitate, the presentation window, exports and devices. Audience room and device never include upcoming rows.
  • Presentation: facilitator:present gains { view: 'map', mapId }.

6. State map files (published; maps repo issue, to be opened)

Section titled “6. State map files (published; maps repo issue, to be opened)”
  • Source: the Protomaps daily planet build (downloads). It is an ODbL Produced Work, and OpenStreetMap attribution is required. Protomaps discourages hotlinking its build server and recommends copying the tileset, so Action Stations hosts its own extracts and the app never contacts the Protomaps build server.
  • Workflow (in the public repository actionstations-ai/maps, free GitHub Actions under ADR-0023, monthly plus manual dispatch): run pmtiles extract <build> us-<st>.pmtiles --bbox=… --maxzoom=15 per state, DC and territory, using boundaries from a committed GeoJSON (US Census cartographic boundaries, public domain), buffered 10 km. Then:
    1. Verify each file with pmtiles verify.
    2. Compute its sha256.
    3. Write catalog.json.
    4. Upload everything as assets of a release tagged YYYY.MM, marked latest.
  • Size rule: each asset must be < 1.9 GiB (the per-file limit is 2 GiB). If a state exceeds it at zoom 15, the workflow retries at zoom 14. If it still exceeds it, the state is split into parts by latitude bands (us-tx-1, us-tx-2), listed under one catalog entry. archives.ts serves parts as one composite source. Sizes are to be measured by the first workflow run. Texas, California and Alaska are the likely splits.
  • Catalog schema (MapCatalog in src/shared/schemas/maps.ts):
  • Trust: the catalog is fetched over HTTPS from the allowed hosts. Each part’s sha256 is checked after download, and a mismatch deletes the file and fails the job. The app does not sign catalogs, matching the hashes-only trust model of packs (docs/packs-format.md).

7. UI

Section titled “7. UI”

Security and privacy

Section titled “Security and privacy”
Threat Mitigation
Network use without consent Online maps off by default, with a settings text that says what the provider sees. Downloads and catalog fetches only on click (or #442 opt-in). Every request is in online.ts/download.ts/area.ts in main, with no renderer fetches.
Breaking provider terms The OSM standard provider gets distinct UA, header-honoured cache, no prefetch and no download or offline save (FR-11). OpenFreeMap areas are capped at 3,000 tiles / 50 MB / 4 parallel with a unique UA (FR-15). The Protomaps build server is never contacted by the app (§6).
Tampered or corrupt state file sha256 per part from the catalog, verified before use, atomic move into the content-addressed store. Archives are read-only afterwards.
Malicious imported archive Size cap (4 GB). PMTiles directory sizes and tile lengths are bounded before reading. MBTiles opens read-only with query_only. A tile is ≤ 2 MB, and gzip inflate is capped at 8 MB.
Remote style pulling arbitrary hosts Online style JSON is rewritten in main to asmap://online/…, and only the provider’s host is fetched. Offline styles ship with the app, and CSP connect-src has no http(s).
Path escape via maps.json Every RelPath must sit under maps/<mapId>/ (safeJoinReal, no symlinks). Store paths derive from sha256 only.
Leaking upcoming injects pinsFor audiences room and device exclude upcoming rows (unit-tested).
License (ODbL, OpenMapTiles) Attribution always visible and exported (FR-18). Catalog files carry license and attribution. The Maps guide explains that sharing a project with copied map data is distributing an ODbL Produced Work.

Open questions

Section titled “Open questions”
  1. State file sizes and splits. Recommendation: zoom 15 everywhere that fits under 1.9 GiB, zoom 14 next, latitude-band parts last. The first run of the maps repo workflow (maps repo issue, to be opened) measures sizes and records them in that repo’s README. Revisit whether zoom 15 is needed once the sizes are known; street-level labels are readable at 14.
  2. Georeferenced site plans (aligning a plan to the geo map with three control points). Recommendation: defer past 0.9.0. Two positions per place (FR-3) cover it without the math.
  3. Shared store vs. project folder. Recommendation: shared app-level store (Design §2), with per-map Copy map data into the project for moving projects between computers. Revisit if facilitators often carry projects on USB drives without the app’s data folder.
  4. Default online provider. Recommendation: OpenFreeMap. It has no key, no request limit, commercial use, and a vector style that matches the offline style family. OSM standard stays a choice for users who prefer it, under its policy.
  5. sha256 or BLAKE3. Recommendation: sha256. It is in Node crypto, fast enough for 2 GB (NFR-4), and matches packs and model downloads. BLAKE3 would add a dependency for no user-visible gain.
  6. Outside the US. Recommendation: catalog format v1 allows any kind. Add EU countries or Canadian provinces when a user asks, through the same workflow, still under the 2 GiB rule.
  7. Catalog update check. Check monthly in the background? Recommendation: only by click, or through the #442 opt-in update check, never on its own (Project rules 3).

Map on devices (#500)

Section titled “Map on devices (#500)”

map.state (host-signed, sealed under the players key) is addressed to one device (client:<id>), not to a role. Servers hand role: and team: frames to every device and the page filters, so a frame per device is what keeps a role’s places off another role’s phone. src/main/live/device-map.ts computes each device’s pins from the releases that reached its seat (all, its role, its team, or the device itself) and were not withdrawn, resends only when a device’s payload changed (after a release, a resend or a withdraw, and when a device joins), and sends closed: true when sharing stops. A site plan’s picture goes once as a sealed blob, shrunk to 1200 px wide when larger and left out when still over the blob cap. A geographic map sends positions only; the device draws a schematic of the places (src/shared/maps/schematic.ts) with a coordinate list, because the device bundle is same-origin and has no tile source. The device shows it under More, with a numbered list as the accessible form. The Facilitate Map tab has a “Map on devices” checkbox while a session runs (live:map-share, live:map-shared).

Tile pyramid (#500)

Section titled “Tile pyramid (#500)”

src/main/maps/pyramid.ts cuts a plan longer than 2048 px into 512 px PNG tiles at halving sizes (level 0 full size, top level one tile) under .cache/maps/pyramid/<mapId>/<size-mtime>/, with done.json written last. It uses Electron’s nativeImage (no new dependency; the spec named sharp). maps:plan-pyramid builds on first use and returns null for small plans; import starts the build in the background. The plan view (PlaneImage, plan-tiles.ts) always draws the top-level tile and the tiles of the chosen level that overlap the frame (at most 48), served through the ttx-media scheme.

Offline labels (#500)

Section titled “Offline labels (#500)”

Noto Sans Regular glyph ranges 0-255 and 256-511 (about 200 KB, SIL Open Font License) sit in components/map/geo/glyphs/ and are served as asmap://l/<fontstack>/<range>.pbf by the renderer protocol; a range that is not bundled loads as an empty stack, so unlisted scripts are skipped rather than failing the map. The Protomaps and OpenMapTiles styles gained place, road and water name layers using name:latin then name. The attribution stays plain text.

Locations pages for geographic maps (#500)

Section titled “Locations pages for geographic maps (#500)”

src/main/export/locations.ts builds a page per geographic map whose places the MSEL uses, up to 12 markers each. A rendered basemap picture needs a WebGL render window that is not built, so the page is a schematic: schematicPoints (shared with the device map) fits the page’s places into a 4:3 frame, the legend lists each place’s rows and “47.6000° N, 122.3400° W”, and the page says “Positions only”. Site plan pages are unchanged.
