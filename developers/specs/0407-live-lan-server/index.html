Spec 0407: Live play: serve sessions from this computer over the room's Wi-Fi

Issue: #407 · Milestone: 0.6.0 · Status: Implemented (ADR-0032; see “Changes in implementation”) · Depends on: #406 · Related: #418 (epic), #408 (relay core reuse), #410 (connection choice), #411 (player page), #417 (dashboard)

Summary

Section titled “Summary”

The desktop app can run a session server itself: it listens on the laptop’s Wi-Fi address, serves the player page and relays the session’s encrypted frames to the devices in the room. No internet, no account, no IT ticket. It starts when the facilitator starts a live session with the connection “This computer” (#410), shows the address and a QR code, and stops when the session ends; nothing listens at any other time.

Requirements

Section titled “Requirements”

User stories

Section titled “User stories”
  • As a facilitator in a training room with guest Wi-Fi and no internet, I want players to join from their phones by scanning a QR code on the projector, so that live play works with what is in the room.
  • As a facilitator, I want to see which address the session is on and switch it if the laptop has several (Wi-Fi, Ethernet, a VPN), so that the QR code points where the phones can reach.
  • As a player on an iPhone or an Android phone, I want to join without installing anything and with at most one certificate warning, so that joining takes under a minute.
  • As an IT reviewer, I want to know exactly which port is open, when, and what it serves, so that I can approve the laptop on our network.

Functional requirements

Section titled “Functional requirements”
  • FR-1 Start and stop. live:session-start with connection lan starts an HTTP(S) + WebSocket server bound to one chosen interface address and a port; live:session-end (or the app quitting, or the Facilitate page being closed with the session ended) stops it and releases the port. The server exists only between these calls.
  • FR-2 Addresses. The app lists the computer’s non-loopback IPv4 addresses with interface names, marks the likely Wi-Fi one as default, and warns when there is none (“This computer is not on a network”) or when only link-local (169.254.*) addresses exist.
  • FR-3 Invite. The Facilitate page shows the join URL, a QR code (≥ 240 px, high contrast, also usable on the presentation window, #417), and a “Copy link” button. The URL carries the session key in its fragment (#406); the QR encodes the same URL.
  • FR-4 Transport security. Default: HTTPS with a certificate the app generates for this session (ECDSA P-256, SAN = the chosen IP address, 7-day validity) and wss:. Alternative, by explicit choice with a warning: plain HTTP and ws: for networks the facilitator trusts. Both keep end-to-end encryption (#406); the choice is about page integrity and the join experience, and the UI says so.
  • FR-5 Fallback transport. Because Safari on iOS refuses WebSocket connections to a certificate it has not trusted even after the page’s warning was accepted, the server also offers a fetch-based transport: GET /v1/sessions/:id/events (server-sent events, one envelope per event) and POST /v1/sessions/:id/send (one envelope per request). The player page (#411) tries WebSocket first and falls back automatically.
  • FR-6 Served routes, nothing else: GET / (a page that says “Scan the QR code” with no session info), GET /s/:sessionId (the player page), GET /assets/* (the player bundle, immutable, hashed names), GET /v1/health, GET /v1/sessions/:id/ws, /events, /send, GET /v1/sessions/:id/blobs/:blobId. Anything else is 404; no directory listing; no file paths from the URL reach the filesystem.
  • FR-7 Server contract. The session logic is the shared relay core (#408): join token check, header validation, routing, in-memory store for catch-up, blob chunks, rate limits, LAN caps from LIMITS.lan (#406). The controller is attached in-process (no WebSocket from the app to itself).
  • FR-8 Firewall guidance. Before the first start on each OS, the page explains the prompt the OS is about to show (macOS “accept incoming network connections”, Windows Defender Firewall “Allow access” with Private networks ticked) and how to recover when it was denied. The app detects “no device could connect for 60 s after the QR was shown” and surfaces that guidance again.
  • FR-9 Status. The Facilitate page shows: listening address and port, HTTPS or HTTP, certificate fingerprint (SHA-256, grouped), connected device count, and a “Stop” button.
  • FR-10 Port. Default 8485; if busy, the next free port in 8485–8495, else an OS-assigned port. The QR always carries the actual port.
  • FR-11 Several sessions. One LAN session per app instance at a time; starting a second asks to end the first.

Non-functional requirements

Section titled “Non-functional requirements”
  • NFR-1 Cost: nothing; no service involved. (CONTRIBUTING, Project rules 1)
  • NFR-2 Privacy: the app opens a listening socket only after the facilitator starts a session with “This computer” selected; the connection screen states what is served and to whom (#410). The server logs connections (time, remote address, client id, close code) to the session’s dashboard and to userData/live/lan.log (rotated at 5 MB × 3), never payloads. No outbound connection is made by the LAN server. (Project rules 3)
  • NFR-3 Accessibility: QR code has a text alternative (the URL) and a “Copy link”; the status line is a live region; firewall guidance is readable at 200 % zoom. WCAG 2.2 AA.
  • NFR-4 Performance: 60 devices on one laptop; fan-out of a 64 KiB frame to 60 sockets in under 50 ms; a 20 MB inject video delivered to 10 devices at once without stalling the UI (the server runs in the main process on the event loop; blob chunks stream from disk with back-pressure, never read whole into memory per client).
  • NFR-5 Platforms: macOS, Windows, Linux (AppImage); works with the display asleep on the laptop (the app asks powerSaveBlocker.start('prevent-app-suspension') for the session’s duration and releases it at end).

Out of scope

Section titled “Out of scope”
  • mDNS / Bonjour names; the QR carries the IP address.
  • Captive-portal detection or Wi-Fi hotspot creation.
  • Internet exposure (port forwarding, tunnels): use the relay (#408).
  • The player page itself (#411) and the controller dashboard (#417).

Design

Section titled “Design”

Module layout

Section titled “Module layout”

out/player/ (the player bundle built by #411) ships as extraResources → app-resources/player/ in electron-builder.yml, next to app-resources/templates/_shared. Unpackaged runs read out/player/ directly (TTX_RESOURCES override as for templates).

Server

Section titled “Server”

startLanServer(opts):

  • node:https with the generated certificate (or node:http), listening on address only (never 0.0.0.0), requestTimeout 30 s, maxHeaderSize default, keepAliveTimeout 65 s.
  • ws WebSocketServer({ noServer: true, maxPayload: LIMITS.lan.envelopeBytes }) upgraded only on /v1/sessions/:id/ws after the join-token check (?j=); each socket becomes a Connection in the relay core hub. Ping every 25 s; a socket silent for 60 s is closed (1001), which emits presence offline.
  • The controller attaches to the hub in-process: hub.attachController(localConnection), where localConnection is a loopback Transport (#406) feeding the app’s LiveClient. No controller token exists for LAN; the in-process attachment is the controller.
  • Blob chunks are stored under userData/live/lan/<sessionId>/blobs/<blobId>/<index> and removed at stop; the in-memory envelope store caps at LIMITS.lan.storedEnvelopes (20,000) and 64 MiB of JSON, after which the oldest receipts are evicted first, then the hub answers relay.error STORE_FULL for new non-controller frames (controller frames are always stored).
  • HTTP headers on every response: Cache-Control: no-store (except /assets/*: public, max-age=31536000, immutable), X-Content-Type-Options: nosniff, Referrer-Policy: no-referrer, Permissions-Policy: camera=(), microphone=(self), geolocation=(), Cross-Origin-Opener-Policy: same-origin, and for HTML: Content-Security-Policy: default-src 'none'; script-src 'self'; style-src 'self'; img-src 'self' blob: data:; media-src blob:; connect-src 'self'; font-src 'self'; manifest-src 'self'; base-uri 'none'; form-action 'none'; frame-ancestors 'none'. 'self' resolves to the LAN origin, so wss:/ws: to the same host is allowed by connect-src 'self' (same-origin WebSocket is covered in current browsers; the header also lists the explicit wss://<host>:<port> / ws://… origin for older ones).
  • Static files: a fixed map built at start from app-resources/player/manifest.json (path → file, content type, size). A request is looked up in the map; it never touches path.join with request input. The player page is the same index.html for every /s/:sessionId (the page reads the id from location.pathname and the key from the fragment).
  • GET /v1/health → { kind: 'lan', version, protocol: [1], caps }; no session information.
  • Errors are JSON { error: { code, message } } without stack traces; 404 for unknown paths, 405 for wrong methods, 413 over size, 429 rate-limited.

Fallback transport (SSE + POST)

Section titled “Fallback transport (SSE + POST)”

Implemented once in relay/core as HttpFallbackAdapter and used by this server and by the Node server (#409); not by the Cloudflare adapter (#408) where WebSockets always work and an open SSE stream would bill duration.

  • GET /v1/sessions/:id/events?j=<joinToken>&client=<clientId>&after=<index> → text/event-stream; the server registers a Connection whose send() writes data: <frame>\n\n; relay.hello first; a comment line every 20 s keeps the stream alive; Last-Event-ID carries the arrival index for resume.
  • POST /v1/sessions/:id/send?j=<joinToken>&client=<clientId> with one envelope as the body (≤ envelopeBytes) → 202 or relay.error JSON. relay.blob.put chunks go through the same endpoint. relay.blob.get responses come down the event stream like any other frame.
  • A client is “connected” while its stream is open; presence works the same.

Why both: Chrome, Edge, Samsung Internet and Firefox accept a wss: connection to a host whose certificate the user clicked through for the page; Safari (iOS and macOS) does not, and gives no prompt. The fetch path inherits the page’s acceptance on every browser. The player page reports which transport it uses in join.ua so the dashboard can show it.

Addresses

Section titled “Addresses”

listLanAddresses() returns, from os.networkInterfaces():

Virtual adapters (utun*, vboxnet*, docker*, br-*, vEthernet*, tailscale*, ZeroTier*) are listed last and never recommended. IPv6 is not offered in v1 (QR length, bracket URLs, phones on IPv4-only guest networks). The list refreshes when the user opens the picker and when the OS reports an interface change (os.networkInterfaces() polled every 10 s while the picker is open).

Certificate

Section titled “Certificate”

cert.ts uses @peculiar/x509 on Node’s WebCrypto to create an ECDSA P-256 key pair and a self-signed certificate per session: CN = Action Stations session <sessionId prefix>, subjectAltName = IP:<address>, notBefore = now − 5 min, notAfter = now + 7 days, key usage digitalSignature, extended key usage serverAuth. The private key lives only in memory and in the TLS context; the fingerprint (SHA-256 of the DER) is shown on the Facilitate page and on the presentation window beside the QR so a player can compare it with what the phone’s warning page shows (Chrome on Android shows it under “Certificate details”; Safari does not show one, which the guide says).

Changing the address after start requires a restart of the server with a new certificate (the SAN must match); the UI does this as one action (“Switch address”) and shows a new QR.

Renderer

Section titled “Renderer”

LanPanel sits inside the Live play section of the Facilitate page (#410 owns the section and the connection selector; this panel is the body shown when “This computer” is selected and the session runs):

  • Before start: address select (recommended first, with interface name and kind), security radio (HTTPS recommended / plain HTTP with a one-paragraph warning), the firewall note for the current platform, “Start session”.
  • Running: QR (SVG via qrcode, aria-label = “Join link: ”), the URL in monospace with “Copy link” and “Show on presentation screen” (#417 adds the QR view to the present route), status line (address, port, HTTPS/HTTP, fingerprint, N devices connected), “Switch address”, “Stop session”. After 60 s with zero connections the firewall guidance appears inline with the OS-specific recovery steps.
  • All strings in src/renderer/src/routes/facilitate/live/strings.ts so the guide and the UI say the same thing.

IPC (channel definitions in src/shared/ipc/live.ts, owned by #410; the LAN fields are):

Events: live:changed (#410) carries { reason: 'started' | 'stopped' | 'presence' | 'error', connected }.

Firewall text (platform-specific, firewall.ts)

Section titled “Firewall text (platform-specific, firewall.ts)”
  • macOS: first start shows “Do you want the application ‘Action Stations’ to accept incoming network connections?” → Allow. If it was denied: System Settings → Network → Firewall → Options → set Action Stations to “Allow incoming connections”. Unsigned builds may ask on every launch.
  • Windows: “Windows Defender Firewall has blocked some features” → tick Private networks → Allow access. If the room’s Wi-Fi is set to Public, Windows blocks incoming connections regardless: Settings → Network & Internet → Wi-Fi → the network → Network profile → Private, or ask IT.
  • Linux: usually nothing; with ufw, sudo ufw allow 8485/tcp (port shown live).

Data

Section titled “Data”

Nothing new in the project folder. userData/live/lan/<sessionId>/ holds blob chunks for the session’s duration and is removed at stop and swept at startup (like packs/.staging). userData/live/lan.log is the rotating connection log. userData/live/sessions/<id>.json (#406) holds the keys.

Security and privacy

Section titled “Security and privacy”
Threat Mitigation
Someone on the Wi-Fi reads exercise content sealed payloads (#406); the server holds ciphertext in memory only
Someone on the Wi-Fi joins the session join token required for /ws, /events, /send; only holders of the invite have it; the facilitator can rotate and kick (#406)
Someone on the Wi-Fi serves a fake page (ARP spoofing, rogue AP) HTTPS with the shown fingerprint is the default; plain HTTP is an explicit choice with the risk named; end-to-end encryption still protects stored and relayed content, not a rewritten page
Path traversal to the laptop’s files static files come from a fixed map; no request string reaches fs; the server never serves outside app-resources/player/
The server stays up unnoticed starts only with the session, stops at session.end, app quit (before-quit → stopLanServer()), window close; the Facilitate page shows “Listening on …” the whole time; TTX_HEADLESS test runs stop it in afterEach
Resource exhaustion from the room LIMITS.lan: 60 clients, 256 KiB envelopes, 60 frames/min/client, 20,000 stored envelopes, blobs 256 MiB / 2 GiB per session; connection attempts over 10/s per address are dropped for 10 s
Certificate private key leak memory only; new key per session
Logs leaking content the connection log has fixed fields; redact() from src/main/packs/fetch.ts style for any URL (fragment never logged)
Binding to all interfaces bound to the chosen address only; a VPN or Ethernet interface is served only if chosen
Firewall prompt denied silently 60-second “no connections” detector with recovery steps

What leaves the computer: the player page and sealed frames, to devices on the chosen network only. No connection is made to anything. The connection screen (#410) says exactly this.

Testing

Section titled “Testing”

Unit (src/main/live/transport/lan/*.test.ts, Vitest under Electron’s Node, loopback only):

  • addresses.test.ts: ranking with fixture networkInterfaces() outputs from macOS, Windows, Linux (Wi-Fi, Ethernet, Docker, VPN, link-local only, none).
  • cert.test.ts: certificate parses, SAN equals the address, validity window, fingerprint format; https server accepts a client that pins the fingerprint.
  • server.test.ts: starts on 127.0.0.1 with port 0; serves /s/<id> with the CSP header set; /assets/<hash>.js immutable; ../ and encoded traversal → 404; unknown route → 404; /v1/health has no session data; WebSocket without ?j= closed 4001; with a valid token gets relay.hello; a full join → welcome → catch-up round trip through the real relay core with two ws clients and the in-process controller; blob put/get through /blobs/:id and over the socket; frame over 256 KiB → closed 4013; rate limit → 4008.
  • fallback.test.ts: SSE stream receives relay.hello and fan-out frames; POST send routes; Last-Event-ID resumes; a dropped stream emits presence offline.
  • stop: port released, blob directory removed, no timers left (vi.getTimerCount()).
  • log.test.ts: rotation; a frame with a fake “payload” never appears in the log.

E2E (Playwright, e2e/live/lan.spec.ts, under E2E=1): launch the app headless with TTX_MOCK_PROVIDERS=1 TTX_LIVE_BIND=127.0.0.1 (the bind override every live e2e uses, epic #418), open an example project’s scenario, start a LAN session on 127.0.0.1 with HTTPS; read the invite URL from the page; open a second browser context (ignoreHTTPSErrors: true) at the invite, join as a player; the app releases an inject (MSEL row with a rendered PNG); the player page shows it; the dashboard shows 1 connected; stop; the player page shows “Session ended”; /v1/health now refuses to connect. A second run uses plain HTTP and the fetch fallback (page.route blocks WebSocket upgrades) to cover both paths.

Packaged smoke (scripts/package-smoke.mjs): app-resources/player/manifest.json and the files it lists exist in the installed app.

Manual, recorded in the PR: iPhone Safari and Android Chrome join over HTTPS (one warning each) and over HTTP; macOS and Windows firewall prompts appear once and the guidance matches.

Changes in implementation

Section titled “Changes in implementation”

Made while building (#407, ADR-0032); the text above is the design, this list is where the code differs and why:

  • Shared core location. relay/core (#408) was not on main when this landed, so the server contract lives in src/shared/live/hub.ts (SessionHub), extracted from MemoryServer, which is now a thin in-process adapter over it. The LAN server’s WebSocket and SSE connections attach to the same hub; the controller attaches through the memory adapter. Convergence with relay/core is a follow-up with #408: one hub, both conformance suites.
  • Hub behaviour fixed to the 0406 text: catch-up never returns a client’s own frames (the earlier MemoryServer did); STORE_FULL is answered to participants without eviction once 20,000 envelopes or 64 MiB are stored, because arrival indexes are array positions and evicting receipts would shift them. Controller frames are always stored.
  • Module layout. src/main/live/transport/lan/ holds server.ts (listener, route table, upgrade), ws.ts, fallback.ts (SSE + POST, here rather than in relay/core; #409 lifts it), connect-params.ts, respond.ts, peers.ts (device set and flood guard), static.ts, cert.ts, addresses.ts, firewall.ts, log.ts. src/main/live/ holds session.ts, seats.ts (join → welcome), invites.ts (links and QR matrices), log.ts (0417 writer), keys.ts. The renderer panel is routes/facilitate/live/LivePanel.tsx (setup and running states in one file), QrCode.tsx, use-live-session.ts, strings.ts.
  • Static files are mapped by walking the bundle folder (index.html plus files with known extensions, depth 4, 2,000 files) rather than from a manifest.json, so the LAN server does not depend on #411’s manifest format. The electron-builder.yml extraResources entry for out/player lands with #411 (its task 3), since electron-builder refuses a missing source.
  • QR codes are computed in main (qrcode) and sent to the renderer as a module matrix the panel draws as one SVG path: no innerHTML, no second QR library in the renderer. The invite URL with its fragment crosses IPC to the panel for display and copy and is never logged.
  • Connect parameters are ?j=<joinToken>&c=<clientId>&r=<resumeToken> on /ws, /events and /send (0406’s names; client= is accepted as an alias for c), all base64url and length-checked before the hub sees them. A malformed set is refused before the WebSocket handshake (HTTP 400) and with 401 on the fallback routes. GET …/blobs/:id?j= requires the join token too.
  • Oversize frames are cut by ws (maxPayload = envelopeBytes, close 1009) and by the fallback (413) before the hub reads them; in process the hub answers relay.error TOO_LARGE. The conformance suite accepts either. There is no close code 4013.
  • Rate limit is a token bucket of 60 frames a minute per participant in the hub (framesPerMinute); the controller is exempt. Connection attempts over 10/s per address are dropped for 10 s. The listener accepts at most 200 sockets; a client whose send buffer passes 8 MiB is dropped.
  • SSE framing: id: <n> and data: <frame> per frame, : keep-alive every 20 s, and a final event: close with { code, reason } so the page sees the same close codes as a WebSocket. A POST is accepted only for an open stream with the same client id and (timing-safe) resume token: 409 without a stream, 401 on a mismatch, 202 when handed to the hub.
  • IPC (src/shared/ipc/live.ts): live:session-start { projectPath, scenarioId, connection, attribution, name? } → LiveSessionStatus, live:session-status, live:session-end → LiveSession, live:lan-addresses, live:lan-switch-address, live:firewall-guidance; event live:changed { reason, sessionId?, connected, message? }. LiveSessionStatus carries the session, the LanServerStatus, both InviteViews (players and staff: URL, epoch, QR matrix) and noConnectionsForMs for FR-8. Shapes are in src/shared/schemas/live.ts.
  • Session log entries carry env.from as the salted clientRef, not the raw client id (0417 FR-4 over FR-2’s wording). Seats: a staff claim without a valid proof is refused not_allowed; a requestedRole outside the scenario is refused; a player without a role is seated without one (0411 owns role choice and the full roster).
  • E2E is e2e/live/lan.spec.ts (start from the Live tab, health over HTTPS, join page in a second context, stop, port refused). Inject release to a phone needs #411 and #412; the multi-client coverage is the conformance suite over real WebSocket and SSE clients and session.test.ts with a real participant LiveClient.

After the security review of the pull request (#457)

Section titled “After the security review of the pull request (#457)”
  • Connect contract (shared with #411, src/shared/live/connect-url.ts): the client id is the only connect parameter in a URL (?client=). The WebSocket carries the tokens in its subprotocol list (as-live.v1, j.<joinToken>, r.<resumeToken>; the server echoes as-live.v1); the stream, send and blob requests carry them in X-AS-Join / X-AS-Resume. A token in a query string is refused (400) so it can never land in a log.
  • Join handshake (#411): a first join without requestedRole gets a lobby welcome (no role, the seats with taken counts); a join naming a seat gets the seated welcome; a device already seated gets its seat back. welcome.roster shows other devices under per-session pseudonyms, never their client ids.
  • Host and Origin: every request must name the bound address:port in Host (421 otherwise); a WebSocket upgrade with an Origin other than the server’s is refused (403).
  • Quotas in the hub: the frame rate limit is per identity (survives reconnects) and per remote address (3×); an address may register at most 4 identities; participants may send 6 catchup.requests a minute; each participant identity has an upload budget of 4 × its blob cap for the session, participants share a 64 MiB pool separate from the controller’s quota, and uploads not completed within 2 minutes are dropped. LIMITS.lan is now 128 MiB a blob and 512 MiB a session, since blobs live in the app’s memory.
  • Back-pressure: an SSE stream whose reader stalls past 8 MiB is dropped; blob downloads stream chunk by chunk with drain, at most two at once per address; /send and /blobs go through the connection flood guard.
  • Plain HTTP is confirmed before start, named as letting anyone on the network read and impersonate session content, and shown as a warning for the whole session. A public (non-RFC 1918) address is refused unless the facilitator confirms (allowPublicAddress).
  • A bind failure rejects live:session-start instead of crashing main; TTX_LIVE_BIND and TTX_PLAYER_BUNDLE apply to unpackaged runs only; a device’s join frames are ignored after 20 in a session (logged once).
  • Rekey grace (REKEY_GRACE_MS, 60 s): the controller opens frames sealed to it under the previous epoch’s players key only within the grace period after a rotation, so a kicked device cannot keep speaking to the controller with an old key.

Open questions

Section titled “Open questions”
  1. Default transport security on the LAN: HTTPS (self-signed) or plain HTTP? Self-signed HTTPS costs one scary warning per device and the Safari fallback; HTTP has neither but lets an attacker on the same Wi-Fi rewrite the page. Recommendation: HTTPS default as the issue says, HTTP as the explicit alternative, and revisit after the first field exercises; the code supports both either way.
  2. Default port 8485 vs an OS-assigned port. A fixed default makes firewall rules and IT approvals possible; recommendation: fixed default with the fallback range, as specified.
  3. Keep the laptop awake. powerSaveBlocker prevents sleep during a session; some facilitators close the lid between phases. Recommendation: block app suspension only (not display sleep), and show “Keep this computer awake while the session runs” in the panel.
  4. IPv6. Recommendation: not in v1; add when a user asks, behind the address picker.
