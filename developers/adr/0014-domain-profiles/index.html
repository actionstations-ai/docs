ADR-0014: Domain profiles — domain-neutral generation as data

Date: 2026-10-22 · Status: Accepted · Issue: #156

Context

Section titled “Context”

The generator was built from the CSAAP airport tabletops, and the airport leaked into code and prompts: facility-fact categories were runways/taxiways/gates/concourses, the media planner’s scene anchors covered four organization types, the lints assumed a cyber incident (a PIO-like role and an IT-like role must get PRESSURE and CLUE/TECH_HURDLE every phase), eleven of twelve default prompts carried airport few-shot examples that a local 30B model copies, and two inject templates (FIDS board, BHS SCADA screen) had no generic equivalent. The owner’s intent is any cyber-physical, emergency-management or operations tabletop: a bus system, physical security at a dam, a private-drone incident, a hospital, a stadium, a city.

Decision

Section titled “Decision”
  • Profiles are data, not code branches. src/shared/domains/ holds a zod DomainProfile schema and thirteen built-in profiles (airport, transit, water_dam, water_utility, energy_utility, healthcare, campus, stadium_venue, port_maritime, municipal, industrial, unmanned_systems, generic). A profile carries: vocabulary (what the facility, the public, the front line and the operations center are called), facility-fact categories (noun + id shape, or a custom regex with the identifier in group 1; lint and complete flags; an optional genericNoun such as Units? that counts only where the context regex matches, #165), typical IT and OT systems, typical player roles, outside parties and regulators, media channels, positive scene anchors for image prompts (public, control, exterior, plus a screenless public for #141), preferred inject types, the threat families it can exercise (first = default), domain-typical NOISE and PRESSURE examples, extra role-heuristic words and an agency pattern. project.orgType selects the profile (ids, legacy values and aliases such as hospital, utility, bus); project.domainProfileOverrides replaces fields per project; any other value is the generic profile, which has no identifier categories and adds no scene anchor.
  • Threat families carry the arc and the rules. Eight families (cyber, physical_security, cyber_physical, uas_drone, insider, natural_hazard, infrastructure_failure, mass_gathering), each with a four-phase arc (titles, goals, beats), decision-point examples, clue and hurdle vocabulary, the key outside party, and lint rules (clueRequired + clueRole; an optional decisionMustMention regex — a drone incident’s decision point must involve law enforcement or the airspace authority). scenario.brief.threatFamily is settled at creation (briefWithThreat): the designer’s choice, else inferred by whole-word keyword hits from the idea and request among the profile’s families, else the profile default. Ideas carry an inferred threatFamily too.
  • One plumbing module. src/main/generate/domain.ts resolves { profile, threat } for a project and scenario, compiles profile fact categories into the code-based FactCategory interface of #161 (categoriesForProfile; the airport profile reproduces the previous extraction exactly), builds the domain and threat prompt variables, and derives the role heuristics (base words plus the profile’s). facility-file.ts extracts with the project’s categories and attaches the definitions to the facts so lint and sheet formatting use them; lintScenario(scenario, domain) and phaseMixGaps take the context (callers without one get the generic profile and the brief’s family, the pre-profile behaviour); anchoredPrompt picks the profile’s public / control / exterior anchor by the prompt’s words; chooseInjectType(row, installed, domainId) treats taxonomy types tagged domains: ['airport'] as unavailable elsewhere; taxonomyVarsFor(profile) lists the domain’s preferred types first and leaves other-domain types out.
  • Prompts are neutral. Every default prompt reads domain and threat; the phase arc, the mix rules, the decision-point and clue vocabulary, the roles, the noise and pressure examples and the outside parties come from them. Illustrations are short and drawn from three or more domains (a water utility, a transit agency, a venue, a hospital); identifiers come only from the project’s facility facts. inject_media_brief adds the profile’s scene anchor in code: after the model’s scene, or as the scene when the prompt has none (#177).
  • Generic templates. info_display_board (airport / transit_bus / rail variants), scada_hmi (water / dam / power / transit_traction), uas_detection_alert, avl_fleet_map, incident_alert_notification (wea / sms / email / siren_pa) and field_report join the taxonomy; fids_board and bhs_scada_screen stay and are tagged airport-only.
  • Reference document sets for two more domains ship under reference/transit/ (Riverbend Regional Transit Authority) and reference/dam/ (Cedar Ridge Dam), fictional and section-numbered with deliberate hooks like reference/ncia/.

Consequences

Section titled “Consequences”
  • Adding a domain is a data file (profile) and, optionally, templates; nothing in the pipeline branches on the domain id except the taxonomy’s domain tags.
  • The facts file (#143) keeps working: the profile only decides which categories are extracted; a user-added section is still shown to the model. Profile categories without lint are shown, not linted.
  • Scenarios created before this ADR have no threatFamily; they lint as cyber under the generic profile until re-created, which is the behaviour they had.
  • The renderer follow-up shipped in #169: a grouped, searchable profile picker (New project, setup wizard, Project settings, with Customize vocabulary editing domainProfileOverrides through project:update), the threat-family choice on the generate brief (suggestion with its reason; the designer’s choice wins), the Templates domain filter, and example projects (examples:list / examples:open).
  • Packs add profiles (ADR-0018, #263): src/shared/domains/registry.ts holds the built-ins plus the enabled packs’ profiles (registerPackProfiles, filled in main by setPackDomainProfiles and in the renderer from domains:list); a pack may not reuse a built-in id or alias. A project on a pack domain keeps domainProfileSnapshot, and resolveProfile(orgType, overrides, snapshot) uses it before the registry.
  • Keyword inference is deterministic and coarse; the designer’s explicit threatFamily always wins, and the ideate output schema could carry an explicit family later (IdeasOutput is unchanged).
